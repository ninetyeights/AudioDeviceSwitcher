## 按时间点切换配置（基础功能已实现，2026-09-19）

- 入口：「工具 → 定时切换配置」。支持每天、指定星期、单次计划，以及新建、编辑、删除、启停、立即试运行。
- 新建／编辑使用独立弹窗；记录计划生效时间，生效前的时间点不补执行。新建、修改规则、重新启用后从下一次时间点开始；旧计划首次升级从当时起算。
- 显示下次执行时间和最近结果；计划单独保存在 `schedules.json`，使用原子写入和备份。
- 当前策略：按电脑本地时间执行，默认错过不补执行；已增加「启动或唤醒后，补执行最近应生效的计划」开关，仅处理最近一条尚未处理的时间点（最近一条已处理则不回退补更早的计划）。配置锁定时仍跳过且记录结果；同一时间按列表顺序仅执行第一条。夏令时不存在的时间跳过，重复时间通过执行记录避免再次执行。
- 应用会话未出现时沿用已有延迟补设逻辑；执行结果区分请求已提交、设备缺失、锁定跳过和异常，不把提交当成完整音频链路验证。
- 已补齐：执行后回读设备和应用路由，显示核对结果并可重试；定时计划和补执行开关纳入备份，兼容旧版备份。导入不携带旧执行记录，从下一次时间点开始。
- 后续可选增强：计划排序、执行历史。目前仅保留最近一次结果。

### 原始需求与验收要点

- 场景：例如工作日 09:00 切换到工作配置，18:00 切换到娱乐配置。
- 支持指定时间、目标配置、启用／停用；考虑单次、每天、指定星期重复，以及多条计划。
- 列表显示下一次执行时间、最近一次执行结果，支持手动试运行。
- 实现前明确：程序未运行或电脑休眠时错过时间是否补执行；时区／夏令时变化如何处理；同一时间多条计划如何确定顺序。
- 与配置锁定、手动切换及其他自动切换规则保持一致：明确优先级，锁定时不静默覆盖，并说明跳过原因。
- 目标配置被删除、设备离线、应用会话未出现时给出准确结果；未出现的会话沿用延迟补设逻辑。
- 验收重点：按时执行、重复计划不重复触发、休眠恢复行为可预期、失败或跳过原因可查看。

## 工作前验证／一键检查（用户需求，优先）

- 场景：开始工作、会议、录音或游戏前，选择对应配置并点击「检查」，确认音频准备情况。
- 检查目标输入／输出设备是否存在、在线、启用，系统默认设备及应用路由是否符合所选配置；检查相关设备／应用的音量、静音状态，以及启用的 Voicemeeter 配置。
- 对照所选配置检查，不要求先应用配置；静音或低音量是否算问题应结合场景预期，避免把有意静音误报为故障。
- 结果区分「通过」「需处理」「等待应用音频会话」「无法验证」，列出原因、受影响应用／设备和可执行的处理操作，不能把等待或读取失败显示成已通过。
- 应用任一方向的音频会话存在时，按现有能力检查输入与输出路由；没有会话时说明尚不能完成验证，不强行启动应用或伪造会话。
- 默认检查只读取状态；提供明确的「重新应用配置」「重试失败项」「打开系统音量合成器」等操作，修复后重新验证。
- 可选交互测试：指定输出设备播放测试音、查看麦克风电平，由用户主动触发；设置检查通过不等于已证明真实声音链路正常。
- 显示检查时间，支持复制结果；检查后配置或设备变化时标记结果已过时。
- 验收重点：工作前能快速看懂是否就绪、哪里有问题、下一步怎么处理；避免给出无法证明的“全部正常”。

## BlueStacks 多实例独立音频路由

- 记录日期：2026-09-19。
- 状态：用户要求暂缓修改，稍后继续；本记录不安排自动提醒或后台修改。
- 需求：在「配置设置 → 应用覆盖」中，为不同 BlueStacks 实例分别保存输入、输出设备配置，切换配置及会话出现后按实例应用。

### 已完成与现状

- 应用来源列表已取消按 EXE 路径去重，分别显示已有音频会话的实例及 PID。
- 当前覆盖规则仍以 EXE 路径为单位，不支持独立实例规则。
- 曾尝试使用程序路径 + `--instance` 稳定标识贯通保存、应用和检测；因底层路由隔离尚未确认，已撤回此实现，避免界面看似独立但实际相互覆盖。

### 已有证据与未确认事项

- 使用两个同路径的临时静音测试进程验证当前 `SetPersistedDefaultAudioEndpoint` 接口：修改 A 的输出偏好后，B 读取的输出偏好也发生变化；测试后恢复原设置。
- 检查到本机三个 BlueStacks 进程的同方向音频会话具有相同的 session identifier。此标识不等同于 session instance identifier，不能单凭它断定系统界面不支持独立路由。
- 尚未直接在 Windows 系统音量合成器中完成 BlueStacks A/B 对照测试，因此不能把测试程序的结果推广成「系统合成器一定无法独立设置 BlueStacks」。
- 音量／静音是会话控制，与输入／输出设备路由是两类能力，需要分别验证。
- 本次诊断中，BlueStacks 的进程路径和启动参数读取曾返回空值；后续要核实实际应用运行权限下的实例识别，不能用临时 PID 作为持久化身份。

### 继续时先做的实际测试

1. 记录两个实例 A、B 的原始设备设置；解除 CKit 锁定并从托盘退出，避免后台恢复干扰。
2. 让 A、B 持续播放不同声音，确保两者在系统合成器中出现；必要时通过分别静音确认条目身份。
3. 只把 A 改到耳机，B 保持扬声器。
4. 检查实际声音去向，并重新打开合成器核对两个设备选择值。
5. 暂停／恢复播放，再重启实例，验证独立设置是否能够持久保存。
6. 恢复原始设置，再启动 CKit。

### 后续实现决策

- 若系统可以独立路由：调查系统使用的身份与接口，按稳定实例标识保存，贯通编辑、删除、切换、延迟补设、偏离检测、锁定及导入导出。
- 若仅当前流能独立，重启后共用：区分临时会话路由与持久化偏好，不承诺重启后保持。
- 若系统操作也会联动：明确现有接口限制，再评估其他实现途径，不保存会互相覆盖的独立规则。
- 保留旧版按 EXE 路径保存的规则兼容性，避免无实例标识时误匹配到其他实例。
